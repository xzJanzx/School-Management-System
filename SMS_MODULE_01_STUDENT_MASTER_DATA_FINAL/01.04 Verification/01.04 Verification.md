# SMS — Module 01 — Student Master Data
Status: COMPLETED

## Verification Principle
Verify actual behavior and persistent evidence. A source file, simulated test, or agent statement is not sufficient evidence by itself.

## Verification Gates

### Build
- type/static checks pass
- production build passes

### Identity
Verify:
- Student Number generated automatically
- Student Number unique
- Student Number immutable
- Student Number never reused
- File Number generated automatically
- File Number unique
- File Number immutable
- File Number never reused

### Identity Preservation
Verify Student Number remains unchanged through:
- academic-year change
- class/grade change
- promotion
- transfer
- re-enrollment

### Validation
Verify required fields cannot be saved incomplete.
Verify National ID validation.

### Duplicate Protection
Create Student A with protected identity data.
Attempt Student B with the same protected identity.
Expected:
- possible duplicate detected
- automatic creation blocked
- Manual Review available
- no silent duplicate identity

### Override
Verify:
- authorized override succeeds
- unauthorized override is denied
- override reason is mandatory
- override is audited

### Sensitive Permissions
Attempt an unauthorized sensitive Student-data modification.
Expected: Access Denied.

### Audit
Verify persistent audit evidence for sensitive operations and duplicate override/status operations as required.

### Status History
Change Student status.
Verify every required historical status entry remains available.

### Search
Verify search by:
- Student Number
- File Number
- name
- National ID

Verify authorization prevents unauthorized data exposure.

### Guardian Integration
Verify Student ↔ StudentGuardian ↔ Guardian integration without a second Student model.

### Document Integration
Verify Student/document relationship without turning Module 01 into a separate document system.

### Historical Integrity
Verify a Student referenced by academic history cannot be deleted in a way that destroys the history.

### Concurrency
Simulate concurrent attempts that could create the same protected identity.
Expected: database/application protections prevent duplicate permanent identities.

### Regression
Verify the approved Foundation and existing module behavior remains intact.

## Gap-Fix Procedure
For every discovered gap:
1. identify the exact requirement;
2. identify the failure;
3. identify the root cause;
4. apply the smallest approved correction;
5. rerun the affected test;
6. rerun Module 01 verification;
7. rerun regression/build checks as required.

Do not rewrite completed functionality unnecessarily.

## Completion
Verification is complete only when the required evidence, tests and build pass and identified gaps are resolved.
