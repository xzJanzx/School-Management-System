## Database
The approved implementation material defines student_transfers with an ID,
unique transfer number, student reference, transfer type/status, source
academic context and enrollment, target academic context where applicable,
external destination metadata, reason, effective date, workflow-user
references, rejection/cancellation metadata, capacity-override metadata,
timestamps, foreign keys, indexes and historical protection.

## Workflow
PENDING → UNDER_REVIEW → APPROVED → EXECUTED.
Alternative approved paths include rejection/cancellation where permitted.

Every transition must define actor, permission, validation, required reason,
data changes, audit event, allowed next states and forbidden transitions.

## Internal Transfer
Validate destination path and capacity. Full-class execution is blocked unless
an authorized capacity override is permitted and justified. Execution must
synchronize enrollment, placement and counters atomically.

## External Transfer
Preserve Student identity and history. The applicable enrollment becomes
WITHDRAWN and the transfer is executed with audit/history persistence.
