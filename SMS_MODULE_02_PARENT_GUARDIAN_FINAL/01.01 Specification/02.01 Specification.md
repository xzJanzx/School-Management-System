# SMS — Module 02 — Parent / Guardian
Status: APPROVED

## Purpose
Module 02 owns the Guardian/Parent domain and its explicit relationships with Students.

Guardian is an independent master entity.
Student is owned by Module 01 and must not be recreated by Module 02.

## Guardian Master
Approved Guardian data includes:
- id
- guardianId
- fullName
- nationalId where supplied
- primaryPhone
- additionalPhone where applicable
- email where applicable
- address where applicable
- canContact
- preferredContactMethod where applicable
- status
- createdAt
- updatedAt

Guardian ID:
- automatic
- unique
- permanent
- immutable
- concurrency-safe

Example format:
GUA-2026-10001

## National ID
If supplied, National ID must be validated and duplicate-protected.
A duplicate candidate must follow the approved duplicate-review workflow rather than silently creating a duplicate Guardian.

## Contact Data
Primary phone is required.
Additional phone, email and address are optional according to the approved model.
CanContact is required.
PreferredContactMethod is a stored preference; it does not create a notification/messaging subsystem.

## StudentGuardian Relationship
The relationship is explicit:

Student
  ↕
StudentGuardian
  ↕
Guardian

The relationship supports:
- StudentId
- GuardianId
- RelationshipType
- IsPrimary
- IsActive
- timestamps
- relationship history

A Student may have multiple Guardians.
A Guardian may relate to multiple Students.

## Primary Guardian
A Student may have at most one active Primary Guardian at a time.

Primary assignment changes must preserve history.
Concurrent attempts must not result in two active Primary Guardians for the same Student.

## Duplicate Protection
Prevent:
- duplicate Guardian identity
- duplicate Guardian National ID where applicable
- duplicate StudentGuardian relationship

Existing Guardian records must be reusable instead of duplicated.

## Lifecycle
Guardian status supports the approved active/inactive/archive behavior.
A Guardian linked to Students must not be hard-deleted in a way that destroys relationship/history integrity.

## Security and Audit
Sensitive Guardian data requires server-side authorization.
Sensitive operations must be audited with actor/action/entity/time and old/new values or reason where required.

## Search and Profiles
Support approved Guardian search and Guardian Profile views.
Support:
- Student → Guardians
- Guardian → Students

## Module 01 Boundary
Module 02 integrates with the existing Student entity and must not create a second Student model or identity system.

## Non-Responsibilities
Module 02 does not own:
- Student Master
- Academic Structure
- Enrollment
- Transfers
- Attendance
- Exams
- Finance
- HR
- Notifications/Messaging subsystem
