# 03.01 — Specification & Implementation Scope
## Module 03 — Academic Structure

**النظام:** SMS — School Management System  
**الموديول:** Student Affairs  
**الحالة:** 🟡 Specification & Scope — جاهز للمراجعة والاعتماد  
**UI/UX:** خارج النطاق

راجعت المواصفات المعتمدة والمرجع الكامل الخاص بـ Academic Structure. الهدف هنا **تثبيت نطاق التنفيذ** فقط، وليس تفكيك كل جزء إلى Acceptance Matrix بعد. المرجع يحدد أن الهيكل الأكاديمي يجب أن يكون **بيانات قابلة للإدارة وليست Hard-Coded**، وأن الـDefault Structure يتم Seed له عند تثبيت النظام ثم يمكن للمستخدم المخول إدارته. fileciteturn1file1

---

## 1. الهدف

Module 03 هو **المصدر المركزي لتعريف الهيكل الأكاديمي للمدرسة**.

وسيستخدمه النظام كأساس لـ:

- تسجيل الطلاب.
- إعادة القيد السنوي.
- الترفيع.
- توزيع الطلاب على الفصول.
- النقل الداخلي.
- النقل بين الصفوف.
- النقل بين المراحل.
- التقارير والإحصائيات.
- التاريخ الأكاديمي.

وبالتالي فالـAcademic Structure ليس مجرد بيانات مساعدة، بل **Domain Foundation** تعتمد عليه الموديولات الأكاديمية الأخرى. fileciteturn1file1

---

# 2. الهيكل الأكاديمي المعتمد

العلاقة الأساسية:

```text id="kdqteb"
Academic Year
      ↓
Stage
      ↓
Grade
      ↓
Class
```

والنموذج المنطقي المعتمد هو:

```text id="9cldhc"
AcademicYear
│
├── AcademicStage
│       │
│       └── Grade
│               │
│               └── Class
│
└── Academic History
        │
        └── Student Enrollment
```

أما العلاقة التشغيلية مع الطالب:

```text id="5z8vwk"
Student
   ↓
Enrollment
   ↓
AcademicYear
   ↓
Stage
   ↓
Grade
   ↓
Class
```

ويجب ألا يمتلك Enrollment تعريف المرحلة أو الصف أو الفصل؛ بل يعتمد على الكيانات المعرفة داخل Academic Structure. fileciteturn1file1

---

# 3. المسار الدراسي المعتمد

الهيكل الأساسي للمدرسة:

```text id="ysbwnh"
Baby Class
    ↓
KG
 ├── KG 1
 └── KG 2
    ↓
Primary
 ├── Grade 1
 ├── Grade 2
 ├── Grade 3
 ├── Grade 4
 ├── Grade 5
 └── Grade 6
    ↓
Preparatory
 ├── Grade 1
 ├── Grade 2
 └── Grade 3
    ↓
Secondary
 ├── Grade 1
 ├── Grade 2
 └── Grade 3
```

والقاعدة المهمة:

> **KG مرحلة مستقلة تحتوي KG1 وKG2، بينما Baby Class مرحلة مستقلة قبل KG.** fileciteturn0file6

---

# 4. نطاق Module 03

سيشمل التنفيذ:

### 03-A — Academic Year

إدارة:

- إنشاء العام الدراسي.
- منع التكرار.
- تحديد العام النشط.
- إغلاق العام الدراسي.
- الحفاظ على تاريخ العام المغلق.
- منع التعارض بين الأعوام النشطة.

وقد حُدد ضمن Acceptance Criteria أنه لا يجوز وجود أكثر من **Active Academic Year** في الوقت نفسه. fileciteturn1file6

---

### 03-B — Academic Stage

إدارة:

- إنشاء المرحلة.
- تعديل المرحلة.
- ترتيب المراحل.
- تفعيل/تعطيل المرحلة.
- تعريف المسار الأكاديمي.
- الحفاظ على العلاقات التاريخية.

والترتيب لا يعتمد على اسم المرحلة؛ بل على **Order/Sequence** معرف داخل الهيكل. fileciteturn1file6

---

### 03-C — Grade

إدارة:

- إنشاء الصف.
- ربط الصف بمرحلة صحيحة.
- تعديل الصف.
- ترتيب الصف داخل المرحلة.
- تفعيل/تعطيل الصف.
- منع العلاقات غير الصحيحة بين Stage وGrade.

مثال:

```text id="k0v071"
Primary
   ├── Grade 1
   ├── Grade 2
   └── Grade 3
```

ولا يجوز ربط KG1 بمرحلة Primary مثلًا. fileciteturn1file15

---

### 03-D — Class

إدارة:

- إنشاء الفصل.
- ربط الفصل بصف محدد.
- Class Code.
- السعة Capacity.
- الترتيب عند الحاجة.
- Active / Inactive.
- تعديل بيانات الفصل.
- إضافة فصول جديدة دون تعديل الكود.

والقاعدة المعتمدة:

> **الفصول النشطة فقط يمكن استخدامها في القيد والنقل.**

كما أن `Class Code` يجب أن يكون فريدًا داخل نطاقه. fileciteturn1file6

---

# 5. Default Academic Structure / Seed Data

عند تثبيت النظام يجب توفير **Default Academic Structure** بالهيكل المعتمد.

ثم يصبح الهيكل:

```text id="4xdewx"
Seed Data
    ↓
Academic Structure
    ↓
Authorized Administration
    ↓
إضافة / تعديل / تعطيل
```

وليس:

```text id="x20nha"
Hard-Coded داخل التطبيق
```

وهذا مهم جدًا لأن المدرسة قد تحتاج مستقبلًا إلى إضافة صفوف أو فصول أو تعديل بنيتها دون تعديل البرنامج نفسه. fileciteturn1file1

---

# 6. Capacity Management

كل Class يجب أن يمتلك:

```text id="5d5fuc"
Capacity
```

ويستخدم النظام هذه القيمة للتحقق من إمكانية تسجيل الطلاب أو نقلهم.

مثال:

```text id="61xben"
Class 3/A
Capacity = 30
Current Students = 30
```

محاولة قيد طالب إضافي:

```text id="8ss6dt"
❌ Normal enrollment blocked
```

لكن قواعد **تجاوز السعة** المعتمدة في Module 04/05 تظل خارج القرار الأساسي للهيكل نفسه؛ Module 03 يوفر بيانات السعة والتحقق منها، بينما Workflow الموافقة والتجاوز يتبع الموديول الذي ينفذ العملية. fileciteturn1file15

---

# 7. Structural Integrity

يجب على النظام ضمان:

```text id="m4uau2"
Stage
  ↓
Grade
  ↓
Class
```

بشكل صحيح دائمًا.

أي:

```text id="uzlcmb"
Class
  MUST belong to Grade
```

و:

```text id="zjo9n5"
Grade
  MUST belong to Stage
```

ولا يجوز إنشاء علاقة غير صحيحة فقط لأن الـIDs موجودة.

مثال ممنوع:

```text id="g951x9"
Stage = Primary
Grade = KG1
```

أو:

```text id="ctvdwh"
Grade = Grade 3
Class = Class belonging to Grade 4
```

هذه القواعد يجب أن تكون **Business Rules داخل Domain/Application/Database**، وليست مجرد قيود UI. fileciteturn1file15

---

# 8. Academic Path Validation

Module 03 مسؤول أيضًا عن تعريف **المسار الأكاديمي الصحيح**.

مثال معتمد:

```text id="5jbplf"
KG2
 ↓
Primary
```

✅ صحيح

بينما:

```text id="aslglt"
KG2
 ↓
Secondary
```

❌ غير صحيح.

وكذلك لا يسمح النظام بالقفز غير الطبيعي بين المراحل.

هذه القاعدة يجب أن تكون في **Business Logic** وليست مجرد منع في الواجهة. fileciteturn1file5

---

# 9. Historical Integrity

هذه نقطة أساسية.

إذا كان الطالب في:

```text id="yo6v44"
2025/2026
Primary / Grade 2 / 2-A
```

ثم أصبح في:

```text id="5e8u66"
2026/2027
Primary / Grade 3 / 3-B
```

فلا يجوز تعديل السجل القديم ليعكس الوضع الجديد.

يجب أن يبقى:

```text id="cg9vs8"
2025/2026 → Grade 2 / 2-A
2026/2027 → Grade 3 / 3-B
```

وبالتالي:

> **تعديل الهيكل الحالي لا يجوز أن يفسد التاريخ الأكاديمي السابق.**

هذه مسؤولية مشتركة بين Academic Structure وEnrollment، لكن Module 03 يجب أن يوفر lifecycle صحيحًا للكيانات حتى يمكن الحفاظ على هذا التاريخ. fileciteturn1file1

---

# 10. Active / Inactive Lifecycle

لا نعتمد الحذف المباشر كوسيلة لإدارة الهيكل التاريخي.

يجب أن تدعم الكيانات الأكاديمية حالة مثل:

```text id="85apqf"
ACTIVE
INACTIVE
```

مثال:

```text id="c34ycb"
Class 3/A
ACTIVE
```

ثم يتم تعطيله:

```text id="ars021"
Class 3/A
INACTIVE
```

ولا يصبح متاحًا للقيود الجديدة، مع بقاء البيانات التاريخية التي استخدمته سابقًا.

ومن القرارات المعتمدة صراحة:

> **لا يتم حذف Class مرتبط بقيود طلابية.** fileciteturn0file7

---

# 11. العلاقة مع Module 04 — Enrollment

Module 03 **لا ينشئ Enrollment**.

وظيفته توفير الهيكل الذي يستخدمه Enrollment:

```text id="15rpc8"
Academic Structure
       ↓
Enrollment
```

والـEnrollment يجب أن يتحقق من:

```text id="bl596o"
Academic Year
   ↓
Stage
   ↓
Grade
   ↓
Class
```

ومن أن الـClass تابع فعليًا للـGrade والـGrade تابع للـStage، وأن الفصل Active وصالح للاستخدام. fileciteturn1file15

---

# 12. العلاقة مع Promotion

الترفيع السنوي يستخدم ترتيب الصفوف داخل الهيكل لتحديد المسار:

```text id="kdlebc"
Current Grade
      ↓
Next Grade
```

لكن Module 03 **لا يقرر نتيجة الطالب**.

فالقرار يأتي من Enrollment/Academic Workflow:

```text id="a3s6oh"
ناجح
 ↓
Next Grade

راسب
 ↓
Same Grade

قرار إداري
 ↓
Next Grade
```

وModule 03 يوفر فقط الهيكل والمسار الذي يسمح بتحديد الصف التالي الصحيح. fileciteturn1file1

---

# 13. العلاقة مع Transfers

Module 03 يوفر للـTransfer Workflow:

- المصدر.
- الوجهة.
- Stage.
- Grade.
- Class.
- المسار الأكاديمي.
- حالة النشاط.
- Capacity.
- صحة العلاقات.

ولا يسمح النظام بوجهة غير موجودة أو غير نشطة. fileciteturn1file1

---

# 14. Permissions

Module 03 يجب أن يخضع لـAuthorization الموجود في النظام.

ولا يجب إنشاء نظام صلاحيات جديد خاص بالموديول.

المستخدم المخول يستطيع إدارة الهيكل وفق الصلاحيات المعتمدة، بينما باقي المستخدمين يستهلكون الهيكل كمرجع للعمليات التي يملكون صلاحيتها.

ويجب تسجيل التعديلات المهمة في:

```text id="a5at4e"
Audit Trail
```

وهذه قاعدة صريحة ضمن Business Rules المعتمدة. fileciteturn1file6

---

# 15. Audit Trail

كل تغيير مهم في الهيكل يجب أن يكون قابلًا للتتبع، مثل:

```text id="41yjio"
Create Academic Year
Update Academic Year
Activate Academic Year
Close Academic Year

Create Stage
Update Stage
Activate/Deactivate Stage

Create Grade
Update Grade
Activate/Deactivate Grade

Create Class
Update Class
Capacity Change
Activate/Deactivate Class
```

ويجب أن نعرف:

```text id="0kbtsf"
Who
What
When
Old Value
New Value
```

بحسب بنية الـAudit infrastructure المعتمدة في النظام.

---

# 16. خارج نطاق Module 03

حتى لا يحدث Scope Creep، **لا يتم تنفيذ** داخل هذا الموديول:

```text id="kubhyt"
❌ Student Master Data
❌ Parent / Guardian
❌ Student Enrollment
❌ Transfer Workflow
❌ Promotion Workflow
❌ Attendance
❌ Exams
❌ Finance
❌ HR
❌ Notifications
❌ Reports implementation
```

لكن يتم توفير **Integration Contracts** اللازمة فقط لتتمكن هذه الموديولات من استخدام Academic Structure.

وبالتالي:

> Module 03 يبني **الهيكل**، ولا يعيد تنفيذ الموديولات التي تعتمد عليه.
