نعم. **نبدأ الآن بتفكيك موديول شئون الطلبة بالكامل، ولا ننتقل لأي موديول آخر حتى نغلقه ونعتبر مواصفاته التنفيذية معتمدة.**

راجعت المرجع المرفوع، والقرار المعماري الأساسي واضح: النظام **Local LAN Multi-User**، بقاعدة بيانات مركزية وAPI مركزي، وتعمل الأجهزة عبر الشبكة المحلية، مع صلاحيات وأثر تدقيقي ونسخ احتياطي. fileciteturn1file1turn1file14

لكن هناك نقطة مهمة: **الملف الحالي لا يحتوي بعد على مواصفات تفصيلية لشئون الطلبة**؛ لذلك لن أخترع متطلبات على أنها متفق عليها. سنبني المواصفات بالتدريج، ونميز بوضوح بين ما تم اعتماده وما يحتاج قرارًا منك.

# 🏫 SMS — Student Affairs
## تفكيك الموديول إلى مواصفات تنفيذية

سأقسم الموديول إلى **12 طبقة**:

### 01 — Student Master Data
البيانات الأساسية للطالب:

- الرقم التعريفي للطالب
- الاسم بالكامل
- الاسم بالعربية
- الاسم بالإنجليزية إن لزم
- تاريخ الميلاد
- محل الميلاد
- النوع
- الجنسية
- الديانة إن كانت مطلوبة
- الرقم القومي
- صورة الطالب
- بيانات الاتصال
- العنوان
- بيانات ولي الأمر
- المستندات

---

### 02 — Academic Enrollment
دورة قيد الطالب:

```text id="pxz4fm"
طالب
 ↓
تقديم
 ↓
قبول
 ↓
قيد
 ↓
فصل دراسي
 ↓
صف
 ↓
فصل
 ↓
حالة الطالب
```

وسنحدد حالات الطالب بدقة، مثل:

- جديد
- مقيد
- مستمر
- منقول
- موقوف
- منسحب
- مفصول
- متخرج

**لكن هذه الحالات لن نعتبرها نهائية قبل اعتمادها.**

---

### 03 — Student Academic History

يجب ألا نكتفي بوجود `Student.ClassId`.

لأن الطالب قد يكون:

```text id="54v9k4"
2025/2026 → الصف الأول
2026/2027 → الصف الثاني
2027/2028 → الصف الثالث
```

لذلك نحتاج **سجل تاريخي للقيد الأكاديمي**.

مثلاً:

```text id="kzk8n7"
Student
   │
   └── Enrollment History
          ├── Academic Year
          ├── Grade
          ├── Class
          ├── Status
          └── Dates
```

وهذا مهم جدًا للتقارير والشهادات لاحقًا.

---

### 04 — Student Documents

إدارة مستندات الطالب:

- شهادة الميلاد
- صورة شخصية
- الرقم القومي
- مستندات التحويل
- مستندات أخرى

والملفات تكون في **Storage مركزي** وليس على جهاز الموظف؛ المرجع نفسه حدد أن ملفات الطلاب يجب أن تكون في تخزين مركزي منظم حسب رقم الطالب. fileciteturn1file16

مثال:

```text id="2yrrd7"
SchoolData
└── Documents
    └── Students
        └── Student-000001
            ├── BirthCertificate
            ├── Photo
            └── OtherDocuments
```

---

# 05 — Student Transfers

نحتاج فصل **النقل** عن مجرد تعديل الصف.

مثلاً:

### نقل داخلي

```text id="x1e1b0"
فصل A
   ↓
فصل B
```

### نقل بين مدارس

```text id="8y9hx6"
مدرسة أخرى
   ↓
مدرستنا
```

أو:

```text id="gbg7zs"
مدرستنا
   ↓
مدرسة أخرى
```

ويجب أن يحتفظ النظام بتاريخ العملية وليس فقط بالنتيجة النهائية.

---

# 06 — Promotion / Academic Progression

عملية الترفيع:

```text id="g0fm9i"
العام الدراسي 2025/2026
الصف الأول
        ↓
ترفيع
        ↓
العام الدراسي 2026/2027
الصف الثاني
```

ويجب أن يكون هناك:

- تنفيذ فردي
- تنفيذ جماعي
- معاينة قبل التنفيذ
- تأكيد
- تسجيل المستخدم الذي نفذ العملية
- تاريخ التنفيذ
- إمكانية معرفة الطلاب الذين لم يتم ترفيعهم

**ولا نسمح للذكاء الاصطناعي بأن ينفذ ترقية جماعية مباشرة بدون Confirmation.**

---

# 07 — Student Search

البحث سيكون من أهم أجزاء الموديول.

يجب أن يستطيع الموظف البحث بواسطة:

- رقم الطالب
- الاسم
- الرقم القومي
- الصف
- الفصل
- الحالة
- العام الدراسي
- ولي الأمر
- رقم الهاتف

مع إمكانية الجمع بين أكثر من فلتر.

مثلاً:

```text id="11nmrk"
العام الدراسي: 2026/2027
الصف: الثالث
الفصل: 3/A
الحالة: مقيد
```

ثم تظهر قائمة الطلاب.

---

# 08 — Student Profile

صفحة الطالب ستكون **مركز المعلومات الرئيسي**.

أقترح أن تحتوي على Tabs:

```text id="9xkugp"
┌──────────────────────────────┐
│ بيانات الطالب                │
├──────────────────────────────┤
│ البيانات الشخصية             │
│ القيد الدراسي                │
│ ولي الأمر                    │
│ المستندات                    │
│ الحضور                       │
│ النتائج                      │
│ المصروفات                    │
│ النقل                        │
│ السجل التاريخي              │
│ Audit History                │
└──────────────────────────────┘
```

وهنا نلتزم بمبدأ مهم:

**الموديول لا يمتلك بيانات الحضور أو الحسابات أو النتائج نفسها.**

بل يعرض البيانات المرتبطة من الموديولات الأخرى عندما تكون متاحة.

# 09 — Parent / Guardian

نحتاج تصميم ولي الأمر ككيان مستقل، وليس مجرد:

```text id="h6hgpe"
FatherName
MotherName
```

لأن نفس ولي الأمر قد يكون لديه أكثر من طالب.

مثلاً:

```text id="9qi2ti"
ولي الأمر
   │
   ├── أحمد
   ├── محمد
   └── سارة
```

وهذا سيفيدنا لاحقًا في:

- التواصل
- الحسابات
- الإخطارات
- التقارير
- متابعة الإخوة

لكن **تفاصيل الحقول والعلاقات النهائية تحتاج اعتمادًا منك.**

# 10 — Student Status & Lifecycle

يجب أن نميز بين:

### البيانات الأساسية

و

### حالة الطالب الحالية

و

### تاريخ الحالات

مثلاً:

```text id="sxm6vs"
طالب
 │
 ├── Active

      ├── New
      ├── Enrolled
      ├── Transferred
      └── ...
```

وبذلك لا نحذف التاريخ السابق عندما تتغير حالة الطالب.

# 11 — Reports

سنقسم التقارير إلى:

### تقارير الطلاب

- كشف جميع الطلاب
- كشف حسب الصف
- كشف حسب الفصل
- كشف حسب الحالة
- بيانات طالب
- كشف الطلاب الجدد
- كشف المنقولين
- كشف المتخرجين

### تقارير القيد

- إجمالي الطلاب
- توزيع الطلاب حسب الصف
- توزيع حسب الفصل
- توزيع ذكور/إناث
- مقارنة الأعوام الدراسية

### تقارير العمليات

- عمليات النقل
- عمليات الترفيع
- عمليات تعديل بيانات الطلاب
- المستخدمون الذين قاموا بالتعديلات

وسنحدد لاحقًا **كل تقرير: الفلاتر + الأعمدة + التجميع + الطباعة + التصدير**.

## لكن لن ننتقل للـ Database بعد

وهذه نقطة مهمة جدًا.

قبل أن نكتب:

- Tables
- Columns
- Foreign Keys
- APIs
- Screens
- Code
- Prompts لـ Google AI Studio

سنقوم أولًا بعمل **تفكيك وظيفي كامل**.

أي أن الخطوة التالية ستكون:

### Student Affairs — Functional Specification

وسنفصل **كل شاشة شاشة**:

```text id="s2vznb"
Screen ID
Screen Name
Purpose
Who Can Access
Fields
Field Type
Required / Optional
Validation
Default Value
Actions
Business Rules
Success
Errors
Permissions
Audit
Related Entities
```

ثم بعد إغلاق الشاشات ننتقل إلى:

**Workflows → Business Rules → Entities → Database → API → Permissions → Reports → Acceptance Criteria → Master Prompt لـ Google AI Studio.**

وهذا أفضل بكثير من أن نبدأ بالكود مباشرة، خصوصًا أنك ستستخدم Google AI Studio في التنفيذ؛ لأن المرجع نفسه يحدد أن العمل سيكون على شكل **Master Specification → Phases → Prompts → تنفيذ → اختبار → إصلاح → المرحلة التالية**. fileciteturn1file14
